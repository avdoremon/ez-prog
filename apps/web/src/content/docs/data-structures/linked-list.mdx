An array packs its values side by side in memory, which is exactly what
makes indexing instant and inserting expensive. A linked list gives up the
"side by side" part entirely: every node lives wherever it happens to be
allocated, holding only its value and a pointer to whoever comes next.

<Viz id="linked-list" />

## How it works

A node holds a **value** and a **pointer to the next node** (or nothing, if
last). The list is a pointer to the first node — the **head**. There's no
second pointer to skip ahead with, so reaching node 3 means walking 0, 1, 2
first: one pointer chase per step, not an array's one-shot arithmetic.

Inserting is the mirror: once you're standing at the right node, splicing in
a new one is two pointer writes, and nothing else moves. An array pays at
insertion, shifting everyone right; a linked list pays at *access*, walking
node by node.

Deleting reverses the rewire: point the previous node's `next` at whatever
the removed node pointed to. No shifting, no gap.

## Try it

<RunnableCode lang="js" client:visible source={`function readThenInsert(head, readIndex, insertAt, value) {
  let node = head;
  for (let i = 0; i < readIndex; i++) node = node.next;
  const found = node.value;

  let prev = null;
  let cur = head;
  for (let i = 0; i < insertAt; i++) {
    prev = cur;
    cur = cur.next;
  }
  const fresh = { value, next: cur };
  if (prev) prev.next = fresh;
  else head = fresh;

  return { found, head };
}

function makeList(values) {
  let head = null;
  for (let i = values.length - 1; i >= 0; i--) head = { value: values[i], next: head };
  return head;
}

function toArray(head) {
  const out = [];
  for (let node = head; node; node = node.next) out.push(node.value);
  return out;
}

const list = makeList([4, 8, 15, 16, 23]);
const result = readThenInsert(list, 2, 1, 99);
console.log('found', result.found);
console.log('list now', toArray(result.head));
`} />

## Trade-offs

Reach for a linked list when you insert or delete at a position you already
hold — the front of a queue, a splice you're already iterating toward.
Avoid it for index access: `list[500]` costs 500 hops where an array
computes the address directly. Iteration suffers too — array values sit in
contiguous cache lines, while linked nodes scatter, so each hop can miss
cache.

An array is cheap to read, expensive to splice; a linked list is the
opposite — your access pattern decides which pays less.

## Check your understanding

1. **Why does reading the node at index 3 cost more in a linked list than
   in an array?**
   - Linked lists store their values in reverse order
   - There is no address arithmetic — you must follow one pointer at a
     time, starting from the head
   - Linked lists are always kept sorted, so the search is slower
   - Every node duplicates the values of the ones before it

   <details>
   <summary>Answer</summary>

   There is no address arithmetic. An array computes `start + index × size`
   in one step; a linked list has no such formula, since nothing says node
   3 lives any particular distance from node 0 — the only way to find it
   is to follow `next` three times from the head.
   </details>

2. **You already hold a reference to the node right before where you want
   to insert. What does the insertion itself cost?**
   - O(n) — every later node has to shift right, same as an array
   - O(1) — rewire two pointers; nothing else in the list moves
   - O(log n), the same as a balanced tree
   - It can't be done without rebuilding the whole list

   <details>
   <summary>Answer</summary>

   O(1). The new node's `next` takes over what used to follow, and the
   node you're standing at points to the new one — two writes, regardless
   of how many nodes come after. The O(n) people associate with linked-list
   insertion is almost always the walk to *find* the position, not the
   splice itself.
   </details>
