A queue serves whoever arrived first. Often you want whoever matters most —
and you want that without paying to keep everything sorted. A heap is the
structure that stays *just* ordered enough.

<Viz id="heap" />

## How it works

A heap is a binary tree, but there are no nodes and no pointers. The tree is
stored in a flat array, and the relationships are arithmetic:

```text
children of i  =  2i + 1  and  2i + 2
parent of i    =  (i - 1) / 2, rounded down
```

Index 0 is the root — the whole representation, which is why a heap costs no
memory beyond the values themselves.

The one rule, for a max-heap: **every parent is at least as large as its
children.** Notice how weak that is: nothing about left versus right, nothing
about cousins — the array above is *not* sorted. It guarantees exactly one
thing: nothing is bigger than the root.

**Insert** appends at the end, then swaps upward while bigger than its
parent. **Extract** takes the root, moves the last value into the hole,
then swaps downward while a child is bigger.

Both walk one path between root and leaf. A binary tree of *n* values is
about log₂(*n*) deep, so both cost log *n*.

## Try it

<RunnableCode lang="js" client:visible source={`function heapInsert(heap, value) {
  heap.push(value);
  let i = heap.length - 1;
  while (i > 0) {
    const p = (i - 1) >> 1;
    if (heap[p] >= heap[i]) break;
    [heap[p], heap[i]] = [heap[i], heap[p]];
    i = p;
  }
  return heap;
}

heapInsert([9, 5, 6, 2, 3], 8);
`} />

## Trade-offs

A heap is the standard priority queue: schedulers, Dijkstra's algorithm, and
"keep the top *k*" all want the extreme element repeatedly, never the full
ordering.

Its cost profile is the point. Sorting costs *n* log *n* up front to know
*every* position; a heap pays log *n* per operation to know only the
extreme — a win when you pull a few items, or values keep arriving.

A heap finds an arbitrary value no faster than scanning, since it never
promised where anything but the root is. Draining it one extraction at a
time is heapsort.

## Check your understanding

1. **Is a heap's array sorted?**
   - Yes — that is how the root ends up largest
   - No: it only guarantees each parent beats its children, which says nothing
     about siblings or cousins
   - Only the first half is sorted
   - Yes, but in descending order

   <details>
   <summary>Answer</summary>

   No. The rule is local — parent versus child — so a smaller value can sit to
   the left of a larger one at the same depth without breaking anything. That
   weakness is the point: maintaining it costs log *n* instead of the *n* log
   *n* a real sort would cost.
   </details>

2. **Why do insert and extract cost about log *n*?**
   - Because half the array is skipped each time, like binary search
   - Because each one swaps along a single root-to-leaf path, and the tree is
     about log₂(*n*) deep
   - Because the array is kept sorted
   - They actually cost *n*, like an array insert

   <details>
   <summary>Answer</summary>

   Each walks one path between root and leaf, and a binary tree holding *n*
   values is about log₂(*n*) deep — so the swap count is bounded by the depth,
   not the size. The array is never sorted, and no shifting occurs: the values
   that move are the ones on that single path.
   </details>

3. **You need to check whether the value 7 is in a heap of 1000 values. How
   fast is that?**
   - Constant time — it is at the root
   - About log *n*, like insert
   - About *n*: the heap says nothing about where non-root values live
   - Impossible without sorting the heap first

   <details>
   <summary>Answer</summary>

   About *n* — you scan. The heap property only relates parents to children,
   so 7 could sit almost anywhere, and there is no branch you can rule out the
   way binary search does on sorted data. Only the *maximum* is free to find.
   You can search it, though, so sorting is not a prerequisite.
   </details>
