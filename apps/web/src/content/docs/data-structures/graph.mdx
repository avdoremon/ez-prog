An array says what comes next. A tree says what comes below. A graph drops
both assumptions and says only what connects to what — which is enough to
model roads, friendships, dependencies, and the web.

<Viz id="graph-intro" />

## How it works

A graph is two sets: **nodes** (also called vertices) and **edges** joining
pairs of them. Two nodes joined by an edge are **neighbours**, and a node's
**degree** is how many edges touch it. Step the visualization to see each
node's degree counted.

Notice the closing frame: the degrees add up to exactly twice the number of
edges. That's not a property of this example — every edge has two ends, so
contributes 1 to each of two nodes. It's the first thing provable about a
graph without knowing anything else about it.

A tree is just a graph with restrictions: connected, and free of cycles. Drop
those and its guarantees go too. There's no root, so no natural starting
point. There may be **cycles**, so a walk can return where it began — why
every graph traversal keeps a `seen` set. Some nodes may be unreachable
entirely.

Edges can be **directed** — a one-way street, a "follows" on social media —
or undirected. Set `directed` to `true` and watch the neighbour lists change:
with direction, being reachable from A no longer means A is reachable from
you.

## Try it

<RunnableCode lang="js" client:visible source={`function describe(values, edges, directed) {
  const adj = values.map(() => []);
  for (const { from, to } of edges) {
    adj[from].push(to);
    if (!directed) adj[to].push(from);
  }
  return { adj, degrees: adj.map((a) => a.length) };
}

const edges = [{ from: 0, to: 1 }, { from: 1, to: 2 }, { from: 2, to: 3 }, { from: 3, to: 0 }];
describe(['a', 'b', 'c', 'd'], edges, false);
`} />

## Trade-offs

An **adjacency list** — each node stores its neighbours — costs space
proportional to nodes plus edges, with immediate neighbour lookup, which is
what traversals need. It's the usual choice.

The alternative, an **adjacency matrix** (an *n*×*n* grid marking edges),
answers "is there an edge from A to B?" in one lookup but costs *n*² space
regardless of edge count — worthwhile only for **dense** graphs. Most real
graphs are sparse, so lists win.

Next, the questions become about *reaching*: what connects to what, how far
apart nodes are, whether a cycle exists.

## Check your understanding

1. **Why do a graph's degrees always add up to twice the number of edges?**
   - Because each node is counted twice
   - Because every edge has two ends, contributing 1 to each of two nodes
   - It is a coincidence of this example
   - Because the graph is undirected and connected

   <details>
   <summary>Answer</summary>

   Every edge contributes 1 to the degree of each endpoint, so summing degrees
   counts every edge exactly twice. It holds for any undirected graph — cyclic,
   disconnected, or with isolated nodes — and does not depend on connectedness.
   </details>

2. **What can a graph do that a tree cannot?**
   - Hold more than two children per node
   - Contain cycles, be disconnected, and have no root
   - Store values
   - Be traversed

   <details>
   <summary>Answer</summary>

   Cycles, disconnection, and the absence of a root. A tree is a connected
   acyclic graph, so it is a graph with those possibilities removed. Trees with
   many children per node exist too, and both structures store values and can
   be traversed.
   </details>

3. **Your graph has 10,000 nodes and about 30,000 edges. List or matrix?**
   - Matrix, because lookups are faster
   - Adjacency list — a matrix would need 100 million cells for 30,000 edges
   - Either; they use the same space
   - Matrix, because the graph is large

   <details>
   <summary>Answer</summary>

   A list. The graph is sparse — 30,000 edges against 100 million possible
   pairs — so a matrix would spend nearly all its space storing "no edge".
   Matrices win on dense graphs, where constant-time lookup is worth the *n*²
   cost; size alone does not decide it.
   </details>
