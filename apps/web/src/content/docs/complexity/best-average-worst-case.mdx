"How long does linear search take on ten values?" has no single answer — it
depends on where the value sits.

<Viz id="linear-search" />

This run looks for 23 and finds it at index 5: six checks. Open **Try your
own input** and change only `target`. Setting `2` ends the run after one
check; setting `100` — absent — costs all ten.

## Three questions, not one

- **Best case** — the cheapest input: the target is first, one check, O(1).
- **Worst case** — the most expensive: absent, or last, *n* checks, O(*n*) —
  nothing can be slower.
- **Average case** — the mean over expected inputs: at a uniformly random
  position, about *n*/2 checks, still O(*n*).

Only the average assumes a distribution data may not match; best and worst
assume nothing.

## When the cases sit in different classes

<Viz id="quick-sort" />

Quick sort partitions around each range's last value: the eight shuffled
values above cost 16 comparisons. Paste
`{ "arr": [1, 2, 3, 4, 5, 6, 7, 8] }` — already sorted — and the count climbs
to 28.

Every pivot is now the largest remaining, so each partition peels off one
element instead of halving it: *n* − 1, then *n* − 2, down to 1 —
*n*(*n* − 1)/2 total. Shuffled input averages O(*n* log *n*); sorted input is
O(*n*²).

Linear search's cases differ only by a constant factor; quick sort's differ
by a whole growth class — calling it O(*n* log *n*) omits the case real data
hits most easily, input already in order. O(·) bounds growth without saying
*which* case; a claim naming none is unfinished.

## Try it

<RunnableCode lang="js" client:visible source={`function checksToFind(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i + 1;
  }
  return arr.length;
}

const arr = [2, 5, 8, 12, 16, 23, 38, 56, 72, 91];
const each = arr.map((v) => checksToFind(arr, v));
const total = each.reduce((a, b) => a + b, 0);

console.log('best', Math.min(...each));
console.log('worst', checksToFind(arr, 100));
console.log('average', total / each.length);
`} />

## Trade-offs

Design against the worst case when slow means broken — a deadline, a control
loop, a backed-up queue. Design against the average when only the total
across runs matters, never the best case: the input you can least rely on
getting.

When a bad worst case is easy to hit, change the algorithm, not the wording:
a random or median-of-three pivot keeps quick sort's O(*n*²) but stops
sorted input from triggering it.

## Check your understanding

1. **Why is sorted input the worst case for the quick sort above?**
   - Sorted arrays take longer to read
   - The last-element pivot is always the largest, so each partition removes
     one value instead of splitting the range in two
   - Comparisons cost more between ordered values
   - It is not — sorted input is its best case

   <details>
   <summary>Answer</summary>

   The last element is the largest on sorted input, so the partition leaves
   *n* − 1 values on one side and none on the other — the opposite of the
   even split quick sort needs, and why this is its worst case, not its
   best. Reading and comparing cost the same whatever the order; the
   shape of the split does all the damage.
   </details>

2. **A service must answer every request inside a fixed deadline. Which case
   should you design against?**
   - Best, so the common path is as fast as possible
   - Average, since most requests are typical
   - Worst, since the deadline applies to every request individually
   - None — deadlines are an operations problem, not an algorithms one

   <details>
   <summary>Answer</summary>

   The worst case: a deadline every request must meet is a promise about the
   slowest one. An average inside it is consistent with a tail that blows
   straight through, and the best case describes only the luckiest request.
   Nor is this only an operations problem — which algorithm you pick is
   what decides how bad that tail can get.
   </details>
