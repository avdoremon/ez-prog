Merging two sorted piles is easy: look at the top card of each, take the
smaller, repeat. Merge sort is built entirely on noticing that a pile of one
card is already sorted.

<Viz id="merge-sort" />

## How it works

Split the array in half, sort each half, merge them — recursion bottoms out
at runs of one value, sorted by definition. All the work is in merging back
up.

Merging: two sorted runs sit side by side; repeatedly compare their front
values and take the smaller. Because both are sorted, that value is the
smallest left anywhere — one pass produces a sorted combination, about *n*
comparisons, not *n*².

Now count: each level merges every value once, costing *n*, and halving
gives about log₂(*n*) levels. Total: **n log n** — and unlike the quadratic
sorts, that holds for every input, since splitting ignores the values.

## Try it

<RunnableCode lang="js" client:visible source={`function mergeSort(arr, lo = 0, hi = arr.length - 1) {
  if (lo >= hi) return arr;
  const mid = (lo + hi) >> 1;
  mergeSort(arr, lo, mid);
  mergeSort(arr, mid + 1, hi);
  const left = arr.slice(lo, mid + 1);
  const right = arr.slice(mid + 1, hi + 1);
  let i = 0, j = 0, k = lo;
  while (i < left.length && j < right.length) {
    arr[k++] = left[i] <= right[j] ? left[i++] : right[j++];
  }
  while (i < left.length) arr[k++] = left[i++];
  while (j < right.length) arr[k++] = right[j++];
  return arr;
}

mergeSort([5, 2, 9, 1, 7, 3]);
`} />

## Trade-offs

Merge sort's selling point: *n* log *n* is guaranteed, not an average. Quick
sort is usually faster but can degrade badly on unlucky input; merge sort has
none.

It is also **stable**: comparisons favor the left run on a tie, keeping
equal values' original order — useful when sorting by one field should
preserve an earlier sort underneath.

The cost is memory: merging needs roughly *n* extra slots, where quadratic
sorts work in place. That flips for data that can't be randomly accessed —
merge sort suits linked lists and data too large for memory, reading each
run front to back.

## Check your understanding

1. **Why does merge sort's cost not depend on how the input is arranged?**
   - It does — sorted input is much faster
   - Because the splitting never looks at the values, so the shape of the
     recursion is the same every time
   - Because it checks for sorted input first
   - Because it uses extra memory

   <details>
   <summary>Answer</summary>

   The split is positional: halve, halve again, regardless of what the values
   are. So every input produces the same log *n* levels with *n* work each.
   Some implementations add a sorted-input shortcut, but plain merge sort has
   none, and the extra memory is unrelated to the timing guarantee.
   </details>

2. **Merging two sorted runs of total length *n* costs how much?**
   - About *n* comparisons — one pass, taking the smaller front value
   - About *n*² comparisons, since every value meets every other
   - About log *n* comparisons
   - It depends on how the values are distributed

   <details>
   <summary>Answer</summary>

   About *n*. Each comparison consumes one value permanently, so one pass over
   both runs is enough — that is precisely what being *already sorted* buys.
   Values from opposite runs never all meet each other, and no comparison is
   skipped, so it is neither quadratic nor logarithmic.
   </details>

3. **What does merge sort spend that bubble and insertion sort do not?**
   - Extra comparisons
   - About *n* extra memory, to hold the merged output
   - Nothing — it is better in every way
   - Time, on already-sorted input

   <details>
   <summary>Answer</summary>

   Memory: the merge needs somewhere to build the combination, roughly *n*
   extra slots, while the quadratic sorts rearrange in place. It makes far
   *fewer* comparisons, and on already-sorted input insertion sort is actually
   the faster one — it finishes in linear time, where merge sort still does
   its full *n* log *n*.
   </details>
