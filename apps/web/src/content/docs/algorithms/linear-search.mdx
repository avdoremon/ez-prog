Handed an unsorted pile of receipts and asked to find one, you do nothing
clever: you go through them one at a time until the right one turns up.
Linear search is that, written down — and its plainness is the point.

<Viz id="linear-search" />

Watch the `checked` counter. It climbs by one per value, and the run stops
the instant a match appears.

## How it works

Walk the array left to right, asking one question at each position: is this
the value I want? If yes, stop and report where. If you reach the end
without a match, report it absent — conventionally `-1`, since no real
index is negative.

That is the whole algorithm: no setup, no requirement on the data. The array
above is sorted only because this visualization is reused to race binary
search in [How Fast Is Fast?](/complexity/big-o/); linear search neither
knows nor cares.

The cost has three cases: first try is one check; last, or absent, is *n*
checks; averaged over random positions, about *n*/2. **You cannot conclude
something is missing until you have looked everywhere.**

## Try it

<RunnableCode lang="js" client:visible source={`function linearSearch(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i;
  }
  return -1;
}

linearSearch([4, 8, 15, 16, 23, 42], 23);
`} />

## Trade-offs

Linear search's advantage is not speed — it demands nothing. Nothing sorted,
indexed, or extra memory. It works on a linked list, a file read a line at a
time, values arriving from a socket. Every faster search buys speed with a
precondition, and something must pay for it.

That makes the comparison against binary search less obvious. Binary search
is dramatically faster, but only on sorted data, and sorting costs more than
a single scan. **For one search on unsorted data, scanning wins** — sorting
first pays off only when you search the same data many times.

When that search happens in a loop, scanning is the wrong tool: sort once
and binary search, or build a hash map.

## Check your understanding

1. **You need to find one value, once, in an unsorted array. Is it worth
   sorting the array first so you can binary search it?**
   - Yes — binary search is always faster
   - No — sorting costs more than the single scan it would save
   - Yes, but only for arrays under 100 elements
   - It makes no difference either way

   <details>
   <summary>Answer</summary>

   No. Sorting costs more than one pass, so you would pay a large setup cost
   to speed up a lookup you could have finished already. Binary search being
   faster *per search* is why the trade-off flips when you search repeatedly
   — the setup is amortized. Size does not rescue it; the costs order the
   same way at any size.
   </details>

2. **What is the worst case for linear search on an array of *n* values?**
   - The value is at the front — 1 check
   - The value is absent — *n* checks
   - The value is in the middle — *n*/2 checks
   - The array is unsorted

   <details>
   <summary>Answer</summary>

   The value is absent, costing all *n* checks — as expensive as being last,
   since both require examining every element. The front case is the *best*
   case, *n*/2 is the average over random positions, and being unsorted costs
   linear search nothing at all.
   </details>

3. **Which of these can linear search run on, that binary search cannot?**
   - An array of numbers
   - A sorted array
   - A stream of values you can only read once, in order
   - An array of exactly one element

   <details>
   <summary>Answer</summary>

   A stream you can only read once, in order. Binary search must jump
   straight to the midpoint, needing random access to data whose order it
   already knows — a stream gives it neither. The other three suit both
   algorithms; a sorted array is where binary search is at its best.
   </details>
